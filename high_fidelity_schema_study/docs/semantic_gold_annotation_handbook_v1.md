# Blind Semantic Gold Annotation Handbook v1

Status: draft for annotator calibration

## Purpose

This handbook defines independently authored gold for the A/B/C/D semantic architecture study. It is not a correction pass over system output. Gold records what approved source evidence supports, including when the correct state is unknown, conflicted, or not applicable.

## Annotator independence

Each case is annotated independently by two people who did not develop the extraction or semantic architecture code.

Annotators may inspect:

- the original dataset resource;
- an approved, frozen documentation bundle;
- a neutral field inventory containing paths, physical dtypes/shapes, explicit attributes, and bounded example values;
- the controlled logical- and semantic-type vocabulary.

The exact neutral packet, approved source bundle, and vocabulary are content-hashed
inputs to each submission. The source bundle contains the only admissible evidence
identities and their approved field paths. An annotator may re-inspect an approved
source at its frozen hash, but may not add an unregistered source after independent
annotation begins.

Annotators must not inspect:

- A/B/C/D outputs;
- model responses, confidence, notes, or evidence choices;
- existing internal pilot gold or semantic annotations;
- deterministic logical/semantic predictions or heuristic hints;
- the other annotator's labels before independent submission.

The neutral field inventory may be generated by deterministic parsing, but predictive logical/semantic/unit fields must be hidden. Explicit file metadata such as a declared unit remains visible as source evidence.

## Unit of annotation

The annotation unit is one `(dataset_id, field_path, property)` slot. Properties are:

- `physical_type`;
- `logical_type`;
- `semantic_type`;
- `unit`.

Every field in the declared gold evaluation scope receives an applicability decision for all four properties. Every semantic target produced by the frozen deterministic task builder must be inside that scope.

## Applicability states

The JSON stores applicability as a boolean and the expected value separately:

| State | `applicability[property]` | Expected value | Meaning |
| --- | :---: | --- | --- |
| Applicable value | `true` | Non-empty value | Evidence supports a specific answer |
| Applicable unknown | `true` | `null` | Property applies, but approved evidence cannot resolve it |
| Not applicable | `false` | `null` | Property does not meaningfully apply to the field |
| Outside scope | Field absent from gold | N/A | Field is intentionally outside this benchmark's evaluation scope |

An applicable known value may never be marked `false`. The string `"unknown"` is not used in blind gold; unresolved applicable properties use JSON `null` with applicability `true`.

Each field also contains a `rationales` object with exactly the same four property
keys. A non-empty property-level rationale is mandatory whenever the value is null,
whether the state is applicable unknown or not applicable. A single field-level
uncertainty string is insufficient because the four properties may have different
reasons.

## Property rules

### Physical type

Use the frozen benchmark vocabulary and the actual file representation, not a convenient analysis-library coercion. Preserve meaningful distinctions required by the protocol. Cite structural evidence.

### Logical type

Assign the field's role, such as identifier, coordinate, time axis, measurement, label, attribute, or group key. A name alone may suggest a hypothesis but does not override contradictory values, structure, or documentation. If the role applies but remains unresolved, use applicable unknown.

### Semantic type

Assign domain meaning only when approved documentation, controlled vocabulary mapping, explicit metadata, or sufficiently specific field evidence supports it. Do not infer a precise semantic type solely because a plausible label is common in the domain. Broad or ambiguous meaning remains applicable unknown.

### Unit

Use a normalized unit only when it is explicit or supported by the approved evidence policy. A unit encoded only in a name must be annotated according to the protocol's frozen evidence rule and recorded as name-derived evidence. Use not applicable for categorical/identifier fields that do not have a measurement unit. Use applicable unknown when a measurement has a unit concept but the unit cannot be resolved.

Gold stores only canonical unit strings from the frozen vocabulary. Listed aliases
such as `%`, `C`, `Celsius`, `hPa`, or `m` must be normalized before submission.
Reference-time units may use only the frozen bounded pattern and retain the normalized
origin. This prevents exact-string scoring from measuring synonym choice instead of
semantic correctness.

## Evidence requirements

Every applicable known value requires at least one gold evidence item. Evidence records contain:

- stable `evidence_id`;
- source type and content-addressed source identity;
- exact field path;
- a location/span or structural selector;
- a short paraphrase explaining support;
- evidence strength: explicit, structural, documentation, value-profile, or name-derived.

Each gold evidence item has its own unique `evidence_id` and also a
`catalog_evidence_id`. The latter must exist in the frozen source bundle and must
authorize the annotated field path. Source hash, source type, selector, and strength
must exactly match the catalog. Deterministic validation establishes identity and
field relevance only; whether the evidence semantically entails the label remains a
human annotation/adjudication responsibility and is never delegated to a judge model.

Quotes are optional; when present they must be short and exactly locatable. Evidence adequacy is recorded separately from correctness.

Applicable unknown and not-applicable decisions require a concise rationale even when no positive evidence item exists.

## Independent annotation workflow

1. Verify the dataset and documentation hashes.
2. Inspect the raw resource and neutral field inventory.
3. Mark evaluation-scope fields.
4. Assign applicability before assigning values.
5. Assign values and evidence independently.
6. Submit an immutable artifact with a unique submission id and content hash.
7. Validate both artifacts independently; an invalid artifact is corrected before any reveal.
8. Compute the deterministic exact-agreement report only after both valid hashes are frozen.
9. Reveal only the generated disagreement worksheet.
10. Produce a consensus artifact while retaining both originals and the disagreement log.

Consensus may resolve ambiguity by re-inspecting approved evidence. It may not consult model output. If consensus cannot be reached, the slot remains applicable unknown or conflicted according to the frozen adjudication rule; it is not forced into a value.

Every disagreement receives exactly one human resolution with a non-empty rationale:
select annotator A, select annotator B, revise using approved evidence, mark not
applicable, or leave unresolved. Agreed slots cannot be silently changed during
consensus. An unresolved slot is stored as applicable null and listed in
`unresolved_slots`, so it does not become a forced applicable-value target.

## Calibration and freeze

Calibration uses non-blind datasets that will never enter the blind benchmark. The team may revise this handbook during calibration. Before blind annotation begins, freeze:

- vocabulary versions;
- evidence policy;
- applicability rules;
- disagreement procedure;
- agreement thresholds;
- annotator artifact schema;
- consensus artifact schema;
- canonical unit aliases and bounded unit patterns;
- approved source-bundle schema and evidence-catalog field relevance;
- validator implementation hash.

Calibration readiness follows
`docs/semantic_annotator_calibration_protocol_v1.md`. Thresholds and the workflow
case set are preregistered in a design file before either independent submission.
The protocol floors are nine cases, 0.80 overall exact state/value agreement, 0.90
applicability agreement, 0.70 agreement for each property, and 0.50 for every
individual case. Evidence-ID agreement is descriptive. A failed round may inform
revisions, but the revised handbook/vocabulary must be confirmed on an entirely
new preregistered calibration case set.

Blind gold is not released to system developers until the benchmark manifest, backend registry, prompts, schemas, power analysis, and execution order are frozen.

## Required artifacts

For each case:

- neutral field inventory;
- approved evidence bundle and hashes;
- annotator-1 JSON;
- annotator-2 JSON;
- agreement report;
- disagreement/adjudication log;
- consensus gold JSON.

The consensus artifact binds both independent submission ids, annotator ids, and
artifact SHA-256 values plus the disagreement-report SHA-256. Post-reveal edits to
either original invalidate the chain rather than silently changing consensus input.

For the corpus:

- sampling and exclusion record;
- annotator-independence declaration;
- vocabulary and handbook hashes;
- dataset-level agreement summary;
- frozen blind manifest.
