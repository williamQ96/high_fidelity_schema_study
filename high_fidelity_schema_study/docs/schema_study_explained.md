# High-School-Level Explanation of a Schema Extraction Research Project

## One-Sentence Summary

We are building a system that can **reliably understand what fields exist inside scientific data files, what those fields mean, which claims have evidence, and which parts are still uncertain.** 

Here, a `schema` can be thought of as the “instruction manual” or “table of contents” for a dataset.

For example, a weather CSV file might contain columns like:

* `station_id`
* `temperature`
* `humidity`
* `dateTime`

Humans can usually guess what these mean. But in scientific research, guessing is not enough. We want the system to answer questions like:

* What type is this field? String, integer, decimal, timestamp?
* What logical role does it play? ID, timeline, measurement, coordinate, label?
* What does it represent in the real world? Temperature, humidity, longitude, latitude?
* What unit does it use?
* Where did this conclusion come from? Column names, sample values, README files, HDF5 attributes?
* How confident are we?

That is the core idea of the project. 

---

# Why We Cannot Simply Let an LLM Guess

If we only give a large language model a filename and a few rows of data and ask it to generate a schema, several problems appear:

* It may guess correctly.
* It may invent fields that do not exist.
* It may present uncertain claims as if they are facts.
* It is difficult for it to explain where its conclusions came from.

Scientific data processing is not suitable for this kind of black-box behavior. We need systems that are:

* Reproducible
* Auditable
* Evidence-based
* Honest about uncertainty

Because of this, the project follows a **deterministic-first** design philosophy.

That means:

> First use deterministic programs to extract structure directly from the file itself, then allow the LLM to add semantic information only when evidence supports it. 

---

# Overall Pipeline

You can think of the system as a production line:

```text
Raw data file
  ->
Detect file type
  ->
Deterministic extractor reads structure
  ->
Generate initial schema
  ->
Record evidence for each decision
  ->
Compare against gold reference
  ->
Allow LLM semantic enrichment with evidence
  ->
Merge validated additions
  ->
Evaluate whether results improve
  ->
Use for retrieval experiments and reports
```

The guiding principles are:

* If something can be reliably extracted from the file, the program should do it first.
* If something is uncertain, the system should not force a guess.
* The LLM can only add information supported by evidence.
* Everything must be measurable and evaluatable.

# Key Components

## 1. Raw Dataset

These are the original scientific data files, such as:

* CSV tables
* HDF5 hierarchical datasets
* Time-series data

These files are the foundation of the project.

Why they matter:

* Schemas must come from real files.
* The system cannot invent descriptions disconnected from actual data. 

---

## 2. Pilot Dataset

The `pilot` corpus is a small, controlled testing collection.

It currently contains 9 internal datasets:

* CSV: easy, medium, hard
* HDF5: easy, medium, hard
* Time-series: easy, medium, hard

This acts like a small laboratory experiment before scaling up.

Why it matters:

* It is risky to start directly with hundreds of complex files.
* Small datasets make debugging easier.
* Difficulty levels test whether the system only works on easy examples. 

---

## 3. Gold Reference

The `gold` schema is a manually created reference answer.

For example, for a field named `temperature`, the gold schema may specify:

* Physical type: float
* Logical type: measurement
* Semantic type: air_temperature
* Unit: Celsius

The gold reference is not generated by the model. It exists so we can evaluate correctness.

Why it matters:

* Without a standard answer, we cannot measure quality.
* “Looks reasonable” is not scientific evaluation.
* We need accuracy metrics and error analysis. 

---

## 4. Deterministic Extractor

This is the core automated extraction program.

It performs tasks like:

* Reading CSV headers
* Inspecting sample values
* Detecting integers, floats, strings, timestamps
* Reading HDF5 groups, datasets, and attributes
* Detecting time axes in time-series data

The important property is consistency:

> The same input always produces the same result.

Why it matters:

* It is stable and reproducible.
* It does not hallucinate nonexistent fields.
* It can directly record evidence such as `header='dateTime'`. 

---

## 5. Derived Schema

The deterministic extractor generates a `derived schema`.

For every field, it records:

* Field name
* Field path
* Physical type
* Logical type
* Semantic type
* Unit
* Example values
* Evidence
* Confidence

Why it matters:

* Later evaluation depends on it.
* LLM semantic enrichment builds on it.
* Retrieval experiments use schema text as searchable information. 

---

## 6. Evidence

Every schema decision should include evidence.

Evidence may come from:

* CSV headers
* Sample rows
* HDF5 attributes
* README documentation
* Filenames
* Metadata records

Example:

```text
Field: temperature
Decision: measurement / air_temperature
Evidence: header='temperature'
Evidence: README mentions weather station data
```

Why evidence matters:

* Without evidence, schema claims are just guesses.
* Evidence allows humans to audit decisions.
* Evidence constrains LLM behavior. 

---

## 7. Evaluation

Evaluation compares the derived schema against the gold reference.

Current baseline metrics include:

* Physical completeness
* Physical accuracy
* Logical accuracy
* Semantic accuracy
* Unit accuracy
* Necessary-field coverage
* Uncertainty behavior
* Error modes

In simple terms:

* Completeness checks whether fields are missing.
* Accuracy checks whether predictions are correct.
* Error modes identify where failures happen.

Why evaluation matters:

* Without evaluation, we cannot tell whether the system improved.
* “Seems better” is not enough. 

---

## 8. Semantic Layer

Deterministic programs are good at structure, but not always good at understanding meaning.

For example, a field called `val`:

* The extractor may classify it as a string.
* A README may explain that it contains numerical observations mixed with “non-detect” markers.
* Therefore, the physical type remains string, but logically it represents measurements.

This is where an LLM can help.

However, the LLM is tightly restricted:

* It may only process specified fields.
* It must rely on evidence.
* If evidence is missing, it must output `unknown`.
* It must produce structured JSON.
* Outputs must pass validation and safety checks.

Why this works:

* LLMs are good at interpreting documentation and context.
* Safety checks prevent uncontrolled hallucinations.

Measured improvements already observed include:

* `csv_hard_field_campaign` logical accuracy improved from `0.6667` to `1.0000`
* `csv_easy_weather_stations` logical accuracy improved from `0.8333` to `1.0000` 

---

## 9. External Corpus

Internal pilot datasets are controlled experiments. External datasets come from real-world repositories such as Dryad and Zenodo.

Current status:

* 16 external retrieval-pool files
* 10 promoted targets
* 6 hard distractors

Why external data matters:

* Internal pilots are relatively clean and idealized.
* Real scientific datasets are messy.
* Retrieval experiments require realistic metadata and field structures. 

---

## 10. Retrieval Experiments

The key question is:

> If a user searches for a dataset containing weather station temperature, humidity, and pressure measurements, can the system find the correct file?

The project compares several retrieval approaches:

* `metadata_only`
* `readme_only`
* `schema_enhanced_deterministic`
* `schema_enhanced_semantic_merged`

Current results:

* `metadata_only recall_at_1 = 0.7000`
* `readme_only recall_at_1 = 0.5000`
* `schema_enhanced recall_at_1 = 1.0000`
* `schema_enhanced_semantic_merged recall_at_1 = 1.0000`

This suggests that schema information significantly improves retrieval quality. 

---

## 11. Schema Source Comparison

The project explicitly separates:

* Deterministic schemas
* Semantic-merged schemas

Why this matters:

* We want to know whether semantic enrichment truly improves retrieval.
* We also want to detect cases where semantic enrichment accidentally hurts performance by adding noisy terms. 

---

## 12. Slice Disambiguation

Some datasets belong to the same family but represent different years, schools, or months.

Examples:

* Greenland cod year1
* Greenland cod year2
* school_5
* school_6
* Data Jan 2019
* Data Mar 2019

These files may have nearly identical schemas.

The system therefore adds slice identifiers such as:

* `year1`
* `year2`
* `school5`
* `jan`
* `first-year`

This helps distinguish related but different files. 

---

## 13. Benchmark Freeze

The project has now moved beyond exploratory experimentation.

The current benchmark slice has been frozen, including:

* 9 internal pilot datasets
* 16 external retrieval-pool files
* 10 promoted targets
* 6 distractors
* Current retrieval systems
* Current regression subsets

Why freezing matters:

* Otherwise, experiments today and tomorrow may evaluate different data.
* Metric changes might reflect dataset drift instead of real improvements.
* Scientific papers require stable evaluation conditions. 

---

## 14. Regression Tests

Regression tests prevent previously working behavior from breaking later.

The project now includes external field-subset tests for high-value fields.

Examples:

### Greenland cod year1

* `Hourbin`
* `COA_Lat`
* `COA_Lon`
* `Tag`
* `Transplant`
* `Cove`

### weatherMQ

* `dateTime`
* `temperature`
* `relativeHumidity`
* `barometricPressure`
* `rainfall`
* `windSpeed`

Why subset testing is used:

* Full gold annotation for all external data is extremely expensive.
* Critical fields still need protection.

# Main Conclusions

## Conclusion 1: Deterministic-first Works

Most structural information can be extracted directly and reliably from files themselves.

## Conclusion 2: LLMs Are Useful, But Must Be Constrained

LLMs work best for:

* README interpretation
* Logical-role inference
* Semantic understanding that deterministic rules struggle with

But they should never freely rewrite schemas.

## Conclusion 3: Schemas Improve Retrieval

Schema-enhanced retrieval clearly outperforms metadata-only and README-only baselines on the current planted retrieval benchmark.

## Conclusion 4: The Current Results Need Protection

That is why the project introduced benchmark freezing and regression testing. 

---

# Remaining Challenges

## 1. Gold References Still Need Secondary Review

Gold annotations themselves must be checked for consistency.

## 2. Time-Axis Accuracy Gaps Remain

Some time-axis evaluation mismatches still exist.

The next step is determining whether the issue comes from:

* The deterministic extractor
* Evaluation logic
* Gold-reference definitions

## 3. External Semantic Merges Are Not Final Gold

External semantic annotations are still high-confidence working annotations, not final human-verified gold references.

## 4. Retrieval Needs Harder Queries

The current retrieval benchmark uses planted queries with known answers.

Future work should include:

* Non-planted queries
* Harder same-family distractors
* More natural-language user questions

# Final Summary

This project is **not** about “letting an LLM guess schemas.”

What it is actually doing is:

1. Reliably extracting structure from scientific files using deterministic programs.
2. Recording evidence for every decision.
3. Evaluating results at the field level using gold references.
4. Allowing LLMs to add semantics only when evidence supports them.
5. Demonstrating that better schemas improve dataset retrieval.
6. Protecting current results through benchmark freezing and regression testing.

The project has now moved from the stage of:

> “Can this be done?”

to the stage of:

> “Stabilize the results, explain them clearly, and prepare them for publication.”
